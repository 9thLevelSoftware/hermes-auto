<task type="auto">
  <name>Task 1: The two-reduction differential harness</name>
  <files>tests/differential/__init__.py, tests/differential/harness.py</files>
  <action>
Build the harness that runs each fixture twice — direct against `MockUpstream`, and through a real gateway pointed at the same mock — and compares both results under two reductions.

Two reductions, because each catches what the other cannot:

- `byte_reduction(frames)` concatenates raw frame bytes and normalizes **only** `id` and `created`. This is what catches a **dropped** frame — most importantly the final usage-only chunk, which a relay can silently swallow while every assembled-JSON comparison still passes. Normalize nothing else; each additional normalization is a class of divergence the harness stops detecting.
- `semantic_reduction(frames)` assembles `tool_calls` by `index`, concatenates `function.arguments` across frames, `json.loads` the result, and returns a structure including `finish_reason` and `usage`. This is what makes a byte-diff **explicable** — it distinguishes "reframed but semantically identical" from "corrupted".

`run_direct(fixture)` drives `MockUpstream` with an HTTP client. `run_through_gateway(fixture)` starts a real gateway configured to point at the mock, sends the same request with a valid inference token, and collects frames. `run_through_gateway` **must drive a real uvicorn sidecar** via `supervisor.start()`. An in-process ASGI app may be added as a fast smoke path but never as the assertion of record — framing defects live in the uvicorn layer, which `TestClient` skips entirely, and finding framing defects is the entire purpose of this plan.

`assert_identical(fixture)` asserts both reductions match and produces a diff naming the first differing frame index and byte offset on failure. A failure message that says only "bytes differ" costs an hour of bisection.

- **`usage_only_final_chunk`**: assert explicitly that the final chunk with `choices: []` and a populated `usage` survives the gateway. A relay that drops it passes every assembled-JSON check, and this is the single most likely silent loss.

<task type="auto">
  <name>Task 3: The chunk-boundary fuzzer and the TTFT gate</name>
  <files>tests/property/test_chunk_boundary_invariance.py, tests/performance/test_ttft_overhead.py</files>
  <action>
**The fuzzer is the highest-yield test in this phase.** SSE relays do not break on well-formed frames; they break on frames split across TCP reads.

Using `hypothesis` (already a dev dependency), take a fixture's upstream bytes and re-split them at arbitrary offsets via `MockUpstream.set_rechunk`, then assert **both** reductions are invariant to the re-split. Content must be identical regardless of how the upstream chunked it.

Strategy: draw a list of split offsets over the fixture length, including degenerate cases — one byte per chunk, one chunk for the whole body, splits landing exactly on a frame boundary, and splits landing inside `data: `. Run over at least `fragmented_arguments`, `fragmented_utf8`, and `usage_only_final_chunk`. Set a `max_examples` that keeps the suite under about 60 seconds and record the number.

If a re-split class is genuinely untestable, record the reason in your summary rather than quietly narrowing the strategy — a fuzzer with an undocumented exclusion is a fuzzer nobody can trust.

**TTFT gate**: `design.md` §15.4 allows under 1% or 100 ms p99 added overhead. Measure with `MockUpstream.set_first_byte_delay(0.3)` — on localhost with no delay the gateway's overhead is invisible, and a gate that always passes measures nothing. For at least 30 iterations, record direct TTFT and gateway TTFT, compute the delta distribution, and assert the **p99** delta is under 100 ms **or** under 1% of direct TTFT. `design.md` §15.4 and PROJECT.md both specify p99; asserting p95 is a strictly weaker gate on exactly the tail the budget exists to bound. Report p95 as context. Skip with a recorded reason when `CI` is set — a shared runner's loop and scheduling jitter breach 100 ms routinely, and a flaky gate gets deleted rather than fixed. Print the full distribution so the number is visible in CI output rather than buried in an assertion.

Also measure with `strict_validation` both off and on, and record both. Plan 02-04 measured the hoisted validator in isolation; this measures it in the request path, which is the number that actually decides the default.
