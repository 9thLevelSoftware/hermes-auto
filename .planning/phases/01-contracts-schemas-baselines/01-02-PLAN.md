**ADR-0001: Provider plugin plus local gateway.** Title it "Route behind the Hermes provider boundary, not inside AIAgent".

`## Context` must state: Hermes treats prompt caching as a core invariant and prefers capabilities at plugin and provider edges; current Hermes policy rejects plugin-controlled per-call model/provider overrides inside `AIAgent`; a proposed failover-routing hook was closed unmerged with maintainers directing users toward configured providers and fallback chains. Cite `design.md §1`.

`## Decision` must state: the integration point is the supported provider boundary. Hermes registers `hermes-auto` as a provider with virtual models, and a local OpenAI-compatible gateway sidecar performs actual selection behind it. Cite `design.md §1` and `§5`.

`## Consequences` — Positive: no Hermes core modification, no private runtime mutation, no fork maintenance, works across every Hermes surface (CLI, TUI, gateway, desktop, cron, subagents), and routing dependencies stay isolated from the Hermes environment. Negative: requires a supervised sidecar process across three operating systems, adds a local HTTP hop to every request, loses access to exact auxiliary task labels and native credential pools, and requires the gateway to reconstruct turn and cache-boundary information that Hermes knows natively.

`## Alternatives Considered` must list the **four rejected rows** of the design.md §3 table with their rejection reasons: mutate `AIAgent` from a plugin (no supported route-replacement API, private-field coupling, upstream policy conflict, likely cache bugs); add a core route-selector hook (maintainers rejected this direction, requires fork maintenance — retained as an optional fork-only track per `design.md §22`); delegation alone (cannot select the parent conversation model); remote routing gateway (privacy, latency, deployment, and service-operability burden — deferred to a later enterprise mode).

The §3 table has five rows total, but the fifth — "register a custom provider pointing at a local gateway" — is the **Recommended** row and is therefore the Decision, not an alternative. Do not invent a fifth rejected alternative to reach five, and do not list the recommended approach under Alternatives.

**ADR-0002: Session and cache switching policy.** Title it "Route on cache boundaries using a four-part route identity".

`## Context` must state: a coding agent makes many model calls per user request; routing each call independently would produce inconsistent tool behavior, destroy prompt caches, and destabilize the agent trajectory. Cite `design.md §6`.

`## Decision` must record the four identities and what each is for — root session (user-visible aggregation, pinning, metrics), lane (a distinct agent or auxiliary execution stream, derived by hashing root session plus normalized system-prompt hash plus tool-schema hash plus initial non-system message hash), user turn (identified from the latest true `role=user` message preceding assistant tool calls; every internal call from that turn shares one route), and cache epoch (ends on new session, prefix discontinuity, compression, system/tool fingerprint change, explicit reroute, target ineligibility, or TTL expiry). Also record the two hard switching rules: routes lock across internal tool loops, and the first-chunk commit barrier forbids splicing a second model into a stream after the first valid SSE event has been forwarded. Cite `design.md §6` and `§8`.

`## Consequences` — Positive: prompt-cache value is preserved, subagents route independently while preserving the root relationship, tool loops stay coherent, and a mid-stream provider failure cannot corrupt tool-call JSON. Negative: the router must reconstruct turn boundaries by inspecting message history rather than being told, lane hashing is sensitive to system-prompt normalization bugs, and a failure after stream commitment must fail the request cleanly rather than recovering.

`## Alternatives Considered`: free per-call routing (destroys caches, destabilizes trajectories); routing only at session start with no re-evaluation (cannot adapt when a long session shifts task type, and cannot respond to a candidate becoming ineligible); mid-stream failover with output splicing (produces duplicate text, corrupt tool-call JSON, conflicting tool identifiers, and untraceable billing per `design.md §8.2`).

Both records use `## Status` = `Accepted — 2026-07-26`.

Read `design.md` §5, §9, §10, and §13 before writing.

**ADR-0003: Model-card architecture.** Title it "Candidates are identity tuples described by versioned model cards".

`## Decision` must record two things. First, a candidate is not a model ID — it is the tuple (provider, endpoint, model, credential scope, protocol adapter, harness profile, harness version), because the same base model through two providers differs in latency, pricing, cache behavior, tool-call reliability, context limits, rate limits, reasoning controls, and safety filters. Second, the six-level metadata precedence chain, in exactly this order: hard operator policy > live health > measured candidate statistics > curated model card > registry metadata > conservative unknown defaults. State that unknown pricing is never represented as zero. Cite `design.md §9.1`, `§9.2`, and `§9.3`.

`## Consequences` — Positive: new models are onboarded by writing a card rather than changing code, the same model through two providers can be scored differently, and every decision can embed the card version it used. Negative: card curation is ongoing manual work, cards can drift from provider reality, and a corrupt or malicious card is a supply-chain surface requiring schema validation and checksums.

`## Alternatives Considered`: treat a model ID as the candidate (loses provider-specific behavior differences); derive all metadata live from provider APIs (unreliable, rate-limited, and unavailable offline); use only Hermes registry metadata (lacks capability scores, domain affinities, and harness profiles).

This ADR is a direct input to plan 01-04, which writes the model-card JSON Schema.

**ADR-0004: Local telemetry and privacy.** Title it "Local-first telemetry with no raw prompt retention".

`## Decision` must record: SQLite in WAL mode as the local event store; the table set from `design.md §13.1`; and the default behaviors — store no raw prompt text, store no tool-result bodies, store no secrets, hash root session identifiers with a local salt, store only derived features and numeric scores, permit local deletion and retention controls, and keep external export opt-in. State explicitly that Hermes's contribution policy requires outbound telemetry and attribution to be gated behind explicit user-facing opt-in. Cite `design.md §13.1`.

`## Consequences` — Positive: the privacy default is safe without configuration, users can delete their own history, and the store is inspectable offline. Negative: derived-feature-only storage limits post-hoc debugging of routing mistakes, salted hashing makes cross-machine correlation impossible by design, and training corpora for Phase 9 require an explicit separate opt-in rather than reusing the default store.

`## Alternatives Considered`: store raw prompts for better debugging and training (violates Hermes policy and creates an exfiltration surface); default-on external export to a hosted analytics service (violates the opt-in requirement); no telemetry at all (makes Phase 8 evaluation and Phase 9/10 learning impossible).

This ADR is a direct input to plan 01-04 (outcome-event schema) and plan 01-06 (privacy documentation).

**ADR-0005: Adapter isolation and rollout tiers.** Title it "Four-tier adapter rollout with an isolated sidecar environment".

`## Decision` must record the four tiers in order with the reason each is at that position: Tier 1 OpenAI-compatible aggregator and local endpoints (one request/response shape, lowest cross-provider replay risk, fastest MVP, covers both hosted and private local candidates); Tier 2 optional LiteLLM as an execution transport only — never the decision engine, run inside the isolated sidecar environment to prevent dependency conflicts with Hermes; Tier 3 direct native adapters added one at a time only after the gateway contract is stable; Tier 4 an optional, version-gated Hermes-native credential bridge that must fail closed and degrade to supported adapters. Record that the router retains ownership of requirements, model cards, hard policy, cost-quality modes, session stickiness, explanations, outcome learning, and health policy regardless of transport. Cite `design.md §10.2`.

`## Consequences` — Positive: a working MVP is reachable with one adapter, dependency conflicts with Hermes are structurally prevented, and the credential bridge is optional so a Hermes upgrade cannot break the product. Negative: Tier 1 alone cannot reach models without an OpenAI-compatible surface, LiteLLM adds a large dependency tree even when isolated, and the Tier 4 bridge requires nightly CI against Hermes `main` to stay viable.

`## Alternatives Considered`: build native adapters first (highest replay risk before the contract is stable); make LiteLLM the routing engine (surrenders policy ownership, which design.md §10.2 explicitly forbids); require the Hermes credential bridge (couples the product to private Hermes internals, contradicting ADR-0001).
