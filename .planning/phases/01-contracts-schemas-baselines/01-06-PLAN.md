Read `design.md` §21 in full — it is the authoritative source and contains exactly fourteen threat rows. Also read §5.3, §8.2, §11.1, and §13.1 for the mitigating mechanisms.

Create `docs/threat-model.md` with these sections in order:

**`## Scope and trust boundaries.`** Describe the four boundaries: (1) Hermes process to gateway sidecar, over loopback HTTP with bearer-token auth; (2) gateway to upstream provider, over the public internet with provider credentials; (3) gateway to local telemetry store, a local SQLite file; (4) the admin API, which per design.md §5.3 uses a different authentication scope and preferably a separate local listener. State explicitly what is out of scope: Hermes's own security posture, upstream provider security, and the security of the operating-system user account running the sidecar.

**`## Assets.`** List what an attacker would want: provider API credentials, the generated local bearer token, the user's prompt and code content in flight, the local telemetry store, routing policy configuration, and model cards.

**`## STRIDE summary.`** A short table mapping each STRIDE category to a one-line statement of how it applies to this system. Use the category names as a **bolded first column with a different column count** than the threats table (two columns: `Category | How it applies`), so the threats-table row gate — which matches a five-column signature with STRIDE in the second cell — does not count these rows. Do not format this summary with five columns.

**`## Threats and mitigations.`** A table with exactly these columns: `Threat | STRIDE | Mitigation | Owning module | Phase`. It must contain one row for each of the fourteen rows in design.md §21, preserving the required mitigation text faithfully. The fourteen threats are:

1. Prompt causes expensive escalation — hard cost ceiling, bounded requirement scores, escalation tier cap, anomaly detection.
2. Prompt attempts to modify router policy — policy never derived from user text; no prompt-triggered configuration commands.
3. Local port accessed by another process — loopback binding, generated bearer token, no CORS, restrictive token-file permissions.
4. Secret leakage in logs — central redaction, credential references rather than values, structured logging allowlist.
5. Malicious model metadata — schema validation, source checksums, operator overrides, conservative defaults.
6. Sidecar dependency compromise — isolated environment, pinned dependencies, lockfile, vulnerability scanning.
7. Raw code exported unintentionally — no raw storage by default, explicit export consent, local retention controls.
8. Cost estimate manipulation — reconcile predicted and actual usage, cap output, unknown price is never zero.
9. Router classifier attack — input truncation, score caps, out-of-distribution detection, deterministic fallback.
10. Model response spoofs route metadata — the gateway, not the target model, sets decision headers and logs.
11. Mid-stream fallback corrupts tools — first-chunk commit barrier; no post-commit model splicing.
12. Concurrent state collision — per-lane locks, transactional state updates, hashed compound keys.
13. Experimental model degrades quality — shadow stage, minimum samples, anomaly circuit breaker, immediate disable.
14. Hermes upgrade breaks private bridge — version gating, compatibility tests, bridge optional and fail-closed.

Assign each row a STRIDE category and an owning module path drawn from design.md §17 (for example `routing/policy.py`, `gateway/auth.py`, `telemetry/retention.py`, `inventory/validation.py`, `adapters/hermes_native.py`), plus the phase that implements it. Most owning modules do not exist yet — that is expected, and naming them is the point: it makes the mitigation traceable when that phase is planned.

Note in the row for threat 14 that the fail-closed probe already exists as `compatibility.py` from plan 01-05, and in the row for threat 5 that schema validation is grounded by the model-card schema from plan 01-04.

**`## Residual risk.`** State honestly what is not mitigated: a compromised operating-system user account can read the token file and the SQLite store; a malicious upstream provider sees the prompts routed to it; the router cannot detect a model that is subtly wrong rather than failing; and cost ceilings bound spend per turn, not per session, until session-level budgets ship.

**`## Review cadence.`** State that this document is reviewed at each phase boundary and that any new external input, new stored field, or new network destination requires a new row before the phase closes.

Include no real credentials, tokens, session ids, or prompt content anywhere, including in examples. Cite `design.md §21` and `docs/adr/0004-local-telemetry-and-privacy.md` explicitly.

<task type="auto">
  <name>Task 2: Write the user-facing privacy guide</name>
  <files>docs/privacy.md</files>
  <action>
Read `docs/adr/0004-local-telemetry-and-privacy.md` and `design.md` §13.1, §13.2, §13.3, §13.4, and §13.5.

Create `docs/privacy.md` written for a user deciding whether to install this, not for a security reviewer. Plain language, no hedging, current state rather than aspiration. Sections in order:

**`## What the router stores.`** Describe the derived data the local store holds, drawn from design.md §13.1 through §13.3: routing decisions and their scores, candidate identifiers, token counts, costs, latencies, health observations, tool-call counts, retry and fallback counts, and explicit feedback. Make it concrete — a short example of a stored record using obviously fake values (candidate `test-hosted-general`, session hash `a1b2c3…`) helps more than a prose list. State that the record shape is defined by the outcome-event schema from plan 01-04 and that the schema structurally rejects anything outside this list.

**`## What the router never stores.`** State the four prohibitions from ADR-0004 as flat declaratives, not as configuration options: raw prompt text is never stored; tool-result bodies are never stored; secrets and credential values are never stored — cards hold references like `env:OPENROUTER_API_KEY`, never the key itself; root session identifiers are hashed with a local salt, so a stored record cannot be linked back to a session id or across machines. Add that the outcome-event schema sets `additionalProperties: false`, so a future change that tried to add a prompt field would fail validation rather than silently start collecting.

**`## Where data lives.`** A local SQLite file in WAL mode under the router state directory (`~/.hermes/auto-router` per design.md §16). Nothing leaves the machine unless external export is explicitly enabled. The gateway binds loopback only and requires a generated bearer token.

**`## Retention and deletion.`** Describe the default retention window (30 days per the design.md §16 configuration example), that it is user-configurable, and that a user can delete the store at any time. Mark the deletion command as arriving in Phase 8 with the telemetry implementation, and say so plainly rather than implying it exists now.

**`## External export.`** State that external export is disabled by default and requires explicit opt-in, per Hermes's contribution policy requiring outbound telemetry and attribution to be gated behind explicit user-facing opt-in. List the optional exporter targets from design.md §13.5 (Langfuse, OpenTelemetry, JSONL, Parquet, Prometheus, team-hosted analytics) and state that even when enabled, only derived routing features, candidate ids, decisions, usage, and policy-approved outcomes are exported — never prompts or code.

**`## Optional code outcomes.`** Describe the design.md §13.4 opt-in: for a repository the user explicitly trusts, the router can record whether a generated diff survived, whether edits were reverted, whether tests passed, and whether a commit was created. State that this is off by default, per-repository, and that these remain local metrics unless the user separately enables export. Mark it as arriving in Phase 8.

**`## Your controls.`** A short table of `Control | What it does | Available from`, covering: disable telemetry entirely, change the retention window, delete the local store, enable or disable external export, enable per-repository code outcomes, and enable the opt-in training corpus for Phase 9. Be accurate about availability — most say Phase 8 or later. Do not list a control that no phase in the roadmap delivers.

Link to `docs/adr/0004-local-telemetry-and-privacy.md` as the authoritative decision record and to `docs/threat-model.md` for the adversarial view.

Use no real credentials, tokens, session ids, paths containing a real username, or prompt content anywhere.
